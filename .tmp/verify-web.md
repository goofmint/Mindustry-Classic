## 診断ログ(計画 Phase 2 Task 1)

### 足したもの
- `World.loadMap()`: 入口と `resetPaths()` の直後で `TimeUtils.millis()` を取り、1 行出す
  `[world] map prototype (256x256, 1 spawns) loaded in 95 ms`
- `Pathfind`: `loadMap()` が呼ぶ `measureInitialPaths()` で初期世代の計測を始める。`update()` の終端分岐(公開成功、到達不能、捕捉した例外)で数え、全スポーンが終わったら 1 行出す
  `[pathfind] initial paths for 1 spawns done in 715 ms (search+smooth 90 ms, 17 frames): published 1, unreachable 0, exception 0`
  - 成功は `pathTiles` を公開した分岐で、`request.pathFound` が真のときだけ数える。探索が終わって `pathFound` が偽なら到達不能
  - 初期世代の途中で別の `resetPaths()`(ウェーブ前の先行計算、`runWave()`、`remakePath()`、別マップのロード)が来たら `aborted by another reset` を 1 行出して計測をやめる
  - スポーン数 0 のときは `initial paths: no spawns` を出す
  - 時刻は `TimeUtils.millis()`(GWT では `System.currentTimeMillis()`)。`System.nanoTime` と共有の `Timers.mark()` は使わない
- `HtmlLauncher`: `System.setOut` に、`println(String)` を `GwtApplication.consoleLog()`(libGDX 既存の JSNI)へ渡す `PrintStream` を入れた

### ブラウザでの読み方
- GWT の `System.out` は Web モードでは何もしない(gwt-user 2.11 の `java.lang.System` エミュレーション。`new PrintStream(null)`)。そのため `io.anuke.ucore.util.Log` の出力はブラウザのコンソールにも出ていなかった
- 計画にあるゲーム内コンソール(グレーブキー)は、ブラウザ版では開けなかった。libGDX 1.13.1 の `DefaultGwtInput` がキーコード 192(グレーブ)を `Keys.UNKNOWN` に変換している(ソースに `// FIXME`)。`console` のキー割り当てに届かない
- 上の `HtmlLauncher` の変更で、ログはブラウザのコンソールに `GWT: ` 付きで出る。Playwright の `console` イベントで読んだ

### 残すか消すか
**残す**。どちらも 1 行のログで、計測中だけ `TimeUtils.millis()` を 1 フレーム数回呼ぶ程度。初期世代が終われば何もしない。経路計算やマップを触るときの退行の確認に使える。`HtmlLauncher` の出力先の変更も、ブラウザ版で `Log` を読める唯一の手段なので残す
- 計測への影響: 探索 1 回ごとに `millis()` を 2 回呼ぶだけで、5 ms の探索予算に比べて無視できる

### 別 Issue にしたい報告
- **N1: ブラウザ版でゲーム内コンソール(グレーブキー)が開かない**。libGDX 1.13.1 の `DefaultGwtInput.keyForCode` がキーコード 192 を `Keys.UNKNOWN` にしている(`// FIXME`)。直すなら `DefaultKeybinds` の `console` を別キーにするか、GWT 側で変換を足す。デバッグ用なので優先度は低い
- **N2: 日本語を TextField に入力できない可能性**。Playwright の `insertText` では日本語が落ちた。実際の IME(composition イベント)での確認が要る。セーブ名やサーバー名に日本語を入れたい場合に影響する
- **N3: 日本語の折り返し**。空白でしか折り返さないので、数字の前後で行が切れ、小書きのカナが行頭に来る。説明文の空白を減らすか、折り返しの規則を足す
- **N4: 防衛**。構成 C を操作なしで動かすと wave 4 でコアを壊されることがある(今回 3 回中 1 回)。Task 5.3 の `docs/BALANCE.md` 6 章の残課題と同じ
- Task 5.1 の B1(ダイアログの背景と減光)、B3(最終セーブが「Fri, 19 Dec 1969」)は今回も再現した(`08-ja-save-load.png`)
- マップ選択の「ハイスコア」は到達ウェーブ(英語の勝利後に 5)を表示している。得点で勝つゲームでは紛らわしい(本家の仕様のまま)

## §8.2 の判断

**数値の基準は要件にも設計にも無いので、以下は暫定の参考基準(初回ロード 3 秒以内、経路計算 2 秒以内、1 ウェーブ目 50 FPS 以上)による判断**。

- 初回ロード約 1.4 秒、マップロード 70〜100 ms、初期経路計算 0.5〜0.9 秒(探索は 0.1 秒前後)、1 ウェーブ目 60 FPS。どれも参考基準に収まり、**重くない**。§8.2 の対策は今は要らない
- **マップ縮小(192×192)**: 要件「256×256 を 3 枚」と矛盾するので、するなら要件変更の判断が要る。今回の数値では必要ない。マップは変えていない
- **`Router.tryDump` の最適化**:
  - 空在庫のガードは `Router.update()` に既にある(`totalItems() > 0` のときだけ `tryDump`)
  - `Router` は `tryDump(tile, tile.getRotation(), null)` を呼ぶ。`Block.tryDump` の方向ループは 4 回回るが、アイテムの走査(73 種)は `i == direction` の 1 方向だけ。**設計書 §8.1 の「73 × 4 方向のループ」は誤りで、1 回の呼び出しで最大 73 回**。ただし `totalItems()`(73 要素の合計)が `update()` と、隣から入れるときの `acceptItem()` で毎回呼ばれるので、Router 1 台あたり 1 フレームでおよそ 73 × 2〜3 回の配列走査になる
  - 初期配置と構成 B/C には Router が無く、今回の計測には効いていない。Router を多数並べた構成(空、混在、出力詰まり)のプロファイルは**未実施**。最適化(非ゼロ ID だけを走査、合計値のキャッシュ)は、そのプロファイルで効果が見えたときに別タスクで提案する
